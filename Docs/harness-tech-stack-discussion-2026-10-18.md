## 一、背景与目标

用户当前使用一份魔改 ZCode，在实际生产任务中的体验较好。但继续在其基础上开发存在以下顾虑：

1. 项目源于他人的开源产品，用户难以完整掌控其源码和架构。
2. 源码与功能范围较大，理解、维护和扩展成本较高。
3. 希望从头开发自己的 harness，以 ZCode 的算法、执行机制和功能作为参考，而不是继续继承整套现有实现。
4. 希望自主选择技术栈，并拥有自研执行内核。

这里的“掌控”主要指执行逻辑、状态语义、依赖边界和扩展方式可理解、可维护、可替换，不意味着必须自研所有底层库。

## 三、对现有 ZCode 的源码观察

### 3.1 它不只是一个 Agent 循环

当前参考项目包含：

- Electron 桌面和 React 界面；
- 独立 CLI/TUI；
- 自研 Agent Runtime、Turn 状态机、工具调度和上下文压缩；
- 模型 Provider 适配、MCP、权限、子代理；
- 跨进程通信、会话同步、任务索引和恢复；
- 内嵌浏览器、终端、文档预览、动态工作流和定时任务等工作台能力。

因此，用户感受到的复杂度不能简单归因于 TypeScript 或 Electron。完整工作台的功能范围、多种运行入口、历史兼容和多层状态同步，都是需要考虑的来源。

**讨论中的判断：**把整套 ZCode 等价翻译为 Go 或 Rust，仍可能得到一个庞大的产品；重新设计清晰的模块边界和功能范围，可能比仅更换语言更重要。这是架构判断，不是已测量的性能结论。

### 3.2 现有结构中值得借鉴的边界

- 核心通过自己的 `Model` 接口调用模型，而不是让特定 Provider SDK 的类型渗透整个内核。
- 工具不仅包含执行函数，还声明只读性、破坏性、并发安全、副作用范围、审批要求、超时和输出预算。
- 普通子代理可以是同进程中的独立逻辑 Runtime，并不必然对应一个操作系统进程。
- 浏览器能力通过 `BrowserControlPort` 抽象，具备执行、取消和会话生命周期接口。
- 存在上下文压缩、工具结果落文件、会话驻留治理、事件缓冲限制和 UI 虚拟化等资源治理机制。

重写时可以参考这些执行语义，而不必照搬包划分、目录结构和全部协议层。

### 3.3 权限与隔离需要区分

源码中的工具审批、会话隔离、子进程管理和操作系统沙箱是不同概念。当前默认执行路径并不提供完整的操作系统级工具沙箱。

更换为 Rust 或 Go，不会自动限制工具对文件系统、网络和凭据的访问；这一点属于独立的安全架构要求。

## 四、Browser Use 的实际架构与限制

### 4.1 桌面内嵌执行面

源码探索显示，当前桌面路径主要使用 Electron `<webview>` guest，并通过 `webContents.debugger` 和 Chrome DevTools Protocol（CDP）执行控制。

能力包括页面状态提取、定位与输入、截图、标签页与弹窗、下载跟踪、录制以及人工交接等。部分 DOM/ARIA 能力依赖固定版本 Playwright 的内部注入脚本，而不是直接连接一个功能完整的标准 Playwright Browser。

这意味着：

- 内嵌浏览器不是只接几条 CDP 命令即可完成的轻量功能。
- Playwright 内部实现依赖会带来升级与兼容维护成本。
- 登录状态、控制权和会话隔离不能混为一谈。当前桌面存在共享持久浏览器分区，控制权按 session 管理，不意味着 cookies 也按 session 隔离。
- 当前有登录数据导入能力，但不能据此保证所有网站的登录状态都能完整迁移。

### 4.2 独立浏览器执行面

参考项目也提供独立浏览器后端：通过 Playwright 启动 Chromium，并可指定 Chrome/Chromium/Edge 可执行文件。

所检查实现的具体行为是：

- 使用 `chromium.launch({ headless: true })`；
- 不等于连接用户正在使用的浏览器及其现有标签页；
- 同一 runtime 可以共享 browser，各 session 创建独立 context；
- 当前设置 `acceptDownloads: false`；
- 不完整具备桌面路径的人工接管、用户标签页认领和持久登录数据复用能力。

因此，现有独立模式不能直接被视为桌面内嵌模式的等价替代。

新项目可以设计有界面的独立浏览器、专用持久 profile 和人工接管，但这些是可实现的候选能力，不是当前参考后端已全部实现的事实。

### 4.3 资源生命周期的影响

源码中的浏览器、context、页面和 Node runner 具有不同生命周期。停止一次请求、分离 debugger、释放控制权、关闭页面和退出浏览器进程，并不是同一件事。

低内存设计应重点考虑：

- 是否为每个任务重复启动浏览器；
- browser/context/page 的共享与隔离边界；
- 页面数量上限和闲置回收策略；
- 哪些登录 profile 必须持久保留；
- 截图和大结果是否跨多层重复缓存；
- 浏览器不用时是否能够退出。

目前没有测量证明某种候选语言或桌面框架在这些场景下必然占用更少内存。

## 五、讨论过的技术栈候选

### 5.1 Go + Wails + TypeScript 前端 + SQLite

**讨论定位：最初的综合均衡候选。**

潜在优势：

- 适合模型流式请求、文件操作、进程管理和任务调度等 I/O 密集工作。
- 并发、取消和超时的实现相对直接。
- 编译、测试、诊断和分发路径较清晰。
- Wails 使用系统 WebView，可以保留 Web 前端生态，而不随桌面壳捆绑完整 Chromium。

主要代价：

- Go 存在垃圾回收，低内存仍依赖对象生命周期和有界缓存设计。
- Provider、终端、Windows 进程管理等仍有适配成本。
- 若使用标准 Playwright，通常仍需浏览器执行层及受控浏览器。
- 系统 WebView 不能直接等价替代完整 Electron 浏览器集成。

补充 Browser Use 要求后，该方案没有被证明不可行，也没有被用户排除；只是讨论中的建议重心转向 Rust 内核与浏览器边界。

### 5.2 Rust + Tauri + TypeScript 前端 + SQLite

**讨论定位：资源控制与长期内核边界优先的候选。**

讨论中提到的组件包括 Rust、Tokio、reqwest、serde 和 SQLite。具体库及版本未选定。

潜在优势：

- 无垃圾回收，内存所有权与资源释放更显式。
- 类型系统有助于表达状态机、执行结果和错误边界。
- 适合扩展文件处理、搜索、解析等本地计算能力。
- Tauri 使用系统 WebView，内核可与桌面壳分离。

主要代价：

- 异步、取消、并发工具和共享状态叠加时，实现复杂度较高。
- 编译反馈和协议适配成本需要纳入开发便利性的评价。
- Rust 不会加快远端模型推理，也不会自动减少外部网页的渲染开销。
- 若另启自动化 Chromium，浏览器活跃时会同时存在 UI WebView 和自动化浏览器。

讨论中对 Rust 的倾向，是基于资源控制和长期可维护边界的判断，不是已通过基准测试得出的最优结论。

### 5.3 TypeScript + Node.js + Web UI

**讨论定位：生态和迭代效率优先的候选。**

潜在优势：

- 模型 SDK、MCP、浏览器自动化和 Web UI 生态便利。
- 可以只实现小型自研内核，而不继承完整 Electron 工作台。
- Provider SDK 可以作为可替换适配层，自研内核并不要求重写所有依赖。

主要代价：

- V8、堆和依赖存在基础资源开销。
- 需要严格限制会话历史、事件缓冲和工具结果缓存。
- 对极低常驻内存目标，需要与原生内核实测比较。

没有证据表明 TypeScript 本身就是当前 ZCode 复杂度或内存问题的唯一来源。

### 5.4 C# + .NET + Avalonia/WPF

**讨论定位：Windows 集成和成熟桌面开发工具链下的候选。**

潜在优势：

- 异步、调试、诊断和系统集成工具成熟。
- WPF 可用于 Windows 桌面，Avalonia 可用于跨平台界面。
- UI 可以不依赖 WebView。

主要代价：

- 存在 .NET 运行时和垃圾回收开销。
- 丰富的 Markdown、代码 diff、终端和文档预览可能需要更多 UI 集成工作。
- 必需的 Browser Use 仍需要浏览器执行后端；不用 WebView 不代表不需要浏览器。

用户随后明确不以语言熟练度作为选型因素。因此，“已经熟悉 C#”或“已经熟悉 Rust”不应作为最终优先级依据。

## 六、补充 Browser Use 要求后的条件性方案

以下是讨论中收敛出的两个重点候选，**不是已作出的选择**。

### 6.1 候选 A：Rust + Tauri + TypeScript/Playwright + 独立 Chromium

适用前提：允许浏览器独立运行，不要求完整的应用内嵌体验。

职责设想：

- Rust 负责 Agent 循环、会话状态、模型适配、工具权限、取消和持久化。
- Tauri 负责桌面窗口与 UI 宿主。
- TypeScript/Playwright 执行浏览器操作并返回结果，不维护第二套 Agent 状态机。
- Chromium 按策略启动、复用和退出。

潜在收益：

- 自动化尽量使用标准 Playwright，减少内嵌 guest 专属适配。
- 浏览器与主界面故障边界较清晰。
- 浏览器不用时，有机会降低基础常驻开销。

需要承担的成本：

- 浏览器活跃时同时存在 UI WebView 和自动化 Chromium。
- 独立窗口、登录 profile、人工接管、浏览器版本与分发需要专门管理。
- 不能仅凭 Tauri 的包体积较小，推出整套系统内存最低。

### 6.2 候选 B：Rust + 精简 Electron + TypeScript 浏览器适配层

适用前提：必须保留应用内嵌浏览器、用户可见操作和顺畅人工接管等体验。

职责设想：

- Rust 负责执行内核和权威会话状态。
- Electron 仅承担窗口、UI、受控页面和必要的本机集成。
- TypeScript 负责浏览器宿主适配，不复制 ZCode 的完整业务服务层。

潜在收益：

- UI 与受控页面可使用同一套 Electron/Chromium 宿主体系，不必一定另启独立 Chrome。
- 嵌入、输入、弹窗、下载和接管更容易整合成一致的桌面体验。
- 避免为绕开 Electron 而自建复杂的 Chromium 嵌入或画面转发系统。

需要承担的成本：

- Electron 的基础资源开销仍然存在。
- 共享宿主不等于共享单一进程，也不保证总内存最低。
- 内嵌页面不自动具备标准 Playwright 的全部能力。
- “精简”指业务职责收缩，不表示浏览器适配本身没有复杂度。

### 6.3 为什么讨论了混合语言，而不是全栈 Rust

浏览器自动化的复杂度主要在导航时序、定位与可交互性、iframe、多页面、登录、上传下载以及失败恢复等方面。

Rust 的 CDP 客户端可以发送浏览器命令，但不自动等价于成熟 Playwright 的完整行为。为了统一语言而重做自动化机制，可能损害开发便利性和可靠性。

因此，讨论中的建议是：自研核心执行语义，同时允许成熟的 TypeScript 浏览器执行层作为可替换适配器。它仍需有清晰的资源、权限和生命周期边界。

## 七、跨候选方案的架构原则草案

以下原则仅作为评估参考，尚未被确认或实施。

```text
CLI / 桌面 UI
       │ 命令与事件
       ▼
Harness 内核
  ├─ Session / Turn 状态机
  ├─ Provider 适配
  ├─ Tool 调度与权限
  ├─ Context / Compact
  └─ 持久化与恢复
       │
       ▼
文件系统 / Shell / MCP / 浏览器执行层
```

1. **内核独立于桌面框架。**更换 UI 不应要求重写 Agent 循环。
2. **权威状态集中。**界面管理显示状态，不独立推进任务状态机。
3. **优先模块边界，而非大量进程和包。**进程按故障隔离与信任边界划分，不按逻辑 Agent 数量划分。
4. **所有增长路径有上限。**包括工具输出、事件缓冲、会话驻留、截图、页面和历史加载。
5. **Provider 接口保留必要语义。**不能为了统一而丢失工具调用 ID、推理签名、缓存控制或流式结束信息。
6. **浏览器执行层不成为第二个内核。**任务决策、审批和持久化归属清晰。
7. **安全边界显式设计。**审批、进程隔离、会话隔离与 OS 沙箱分别评估。

## 八、值得从 ZCode 继承的行为，而非实现层数

- Turn 状态转换、中断与取消传播。
- 模型流式输出跨过可见或有副作用边界后的重试规则。
- 工具输入校验、权限裁决、并发条件和结果预算。
- 上下文裁剪、微压缩和总结压缩。
- 会话恢复、命令去重和陈旧消息防护。
- 子代理结果收集与生命周期治理。
- Browser Use 的会话归属、人工交接、异常恢复和资源释放。

可被重新审视的范围包括历史兼容、多入口交付、复杂任务投影、文档工作台和工作流等。但是否保留这些功能尚未决定，不能将其视为已批准删除。

## 九、验证“最优”所需的评估维度

本节是候选评估参考，不构成已安排的实施任务。

### 9.1 资源与性能

应区分以下指标：

- 发布包体积与运行内存。
- 内核进程内存与整棵进程树的资源占用。
- 空闲、普通 coding 任务、Browser Use 活跃和多会话并发场景。
- 冷启动时间、首次浏览器可用时间、取消响应和资源释放时间。
- 长时间运行后的内存增长、残留页面和孤儿子进程。

不同操作系统的工作集、私有内存和 RSS 口径并不完全相同；比较时需要统一统计方法，并考虑共享内存重复计数问题。

### 9.2 功能与可靠性

- 同类生产任务完成率和错误恢复能力。
- Browser Use 的定位、截图、导航、iframe、弹窗和多标签页表现。
- 登录持久性、人工接管、上传下载和异常关闭后的恢复。
- 会话中断恢复、工具取消、外部进程树清理。
- 不同 Provider 下的工具调用、推理内容和流式语义兼容。

### 9.3 开发与维护成本

不考虑个人当前熟悉哪门语言，但仍应评价：

- 语言和异步模型自身带来的实现复杂度。
- 稳定公开 API 与内部实现依赖的比例。
- 原生依赖、浏览器版本和跨平台打包的维护工作。
- 新增 Provider、工具、页面能力和 UI 功能时需要改动多少层。
- 测试、日志、回放和故障诊断是否容易建立。

### 9.4 生产效果基线

现有 ZCode 的实际生产表现可以作为行为基线。讨论中建议，将成功任务和失败案例整理为评测场景，在控制模型、提示和工具契约差异的前提下，对比任务完成率、耗时、token 消耗和资源占用。

目前未建立或执行这些评测，因此不能声称任一候选已经优于现有实现。
