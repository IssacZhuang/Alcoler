## 一、实验要回答的问题

讨论报告中的候选不是同一维度的选项：5.1–5.4 混合了内核语言与桌面框架，候选 A/B 又叠加了浏览器执行形态。直接"四个方案各做一个完整产品再比"代价过高。因此拆为五个可独立测量的问题：

| 编号 | 问题 | 对应讨论报告条目 | 回答该问题的实验 |
| --- | --- | --- | --- |
| Q1 | Agent 内核用哪种语言实现，在真实工作负载下资源与性能差异是多少？ | 5.1–5.4 的内核部分 | E1 |
| Q2 | Browser Use 用哪种执行形态（独立 Playwright Chromium / Electron 内嵌 webview+CDP / CDP 接管真实浏览器），能力与资源代价如何？ | 4.1、4.2、6.1、6.2 | E2 |
| Q3 | 桌面外壳（Tauri / Electron / Wails / Avalonia）本身的资源与体验代价如何？ | 5.1–5.4 的桌面部分 | E3 |
| Q4 | 在各内核上完成同一组标准变更任务，开发与维护代价差异是多少？ | 9.3 | E4 |
| Q5 | 幸存组合端到端跑生产任务，相对现有 ZCode 基线表现如何？ | 9.4 | E5 |

Q1、Q3、Q4 相互独立可并行；Q2 独立于内核语言（浏览器执行层讨论中已倾向 TypeScript/Playwright 作为可替换适配器）；Q5 只对前四项的幸存者执行。

## 二、总体设计原则

1. **控制变量。** 同一台机器、同一 OS 镜像状态、锁定的依赖版本（WebView2 运行时、Chromium、Playwright、SQLite）。性能测量一律使用本地确定性 mock provider 回放，消除网络与远端模型抖动；真实 provider 只用于 E5 的语义与生产对照。
2. **统一度量。** 全部实验共用 E0 的采样与统计规范（第三节），内存以进程树聚合、私有内存为主口径，避免共享内存重复计数。
3. **阶段门禁。** 廉价实验先淘汰有致命缺陷的候选，昂贵的端到端原型（E5）只对幸存者执行。
4. **黑盒契约。** E1 的四个内核 spike 暴露同一 CLI/JSONL 行为契约（附录 A），使测量脚本、工作负载回放和黑盒测试套件跨语言复用，防止"各写各的、比了个寂寞"。
5. **语言熟悉度隔离。** 讨论报告明确不以语言熟练度选型。E4 通过规格化任务书 + 共享黑盒测试度量"任务规格符合度与改动面"，开发者速度仅作记录项不作评分项（混淆因素见 12.1）。
6. **数据与决策分离。** 实验产出数据与门禁结论；内嵌浏览器是否为硬性产品要求、各维度权重，属于用户决策，本文只标记输入槽位（第十一节）。

## 三、E0：统一度量规范与测试基础设施

**目的：** 先固定"怎么量"，再开始量。所有实验复用本节产物。

### 3.1 内存口径

- **主口径：进程树 Private Bytes（私有提交内存）求和。** 私有内存不会跨进程重复计数，适合对比。
- **辅口径：进程树 Working Set 求和**，单独报告并注明共享页（如 WebView2、Electron 多进程共享的 Chromium 页）会重复计数。
- 采样：1 Hz，记录 `时间戳, pid, ppid, 进程名, privateBytes, workingSet`，离线按检查点聚合成进程树。
- **检查点定义：**
  - `idle`：启动后静置 60 秒；
  - `streaming`：模型流式输出进行中；
  - `toolburst`：连续工具执行期间；
  - `settle`：任务结束后再静置 60 秒，并在可用的语言强制 GC/回收后二次采样（Go `debug.FreeOSMemory`、.NET `GC.Collect`、Node `--expose-gc`、Rust 释放后分配器 trim），报告两个值；
  - `browser-open` / `browser-closed`：浏览器首次可用后 / 全部页面关闭并回收后；
  - `soak-delta`：长时运行末值减初值。
- 实现方式：PowerShell 采样脚本 + Python 汇总脚本，输出 CSV 与 Markdown 报表。

### 3.2 时间口径

- 冷启动到 ready（内核：事件口可接收命令；外壳：主窗口可交互）。
- 流式首字节转发开销：mock provider 发出首个 SSE 事件到内核 stdout 出现首个 `model_delta` 的耗时。
- 取消响应：发出 cancel 命令到工具进程树完全退出（p99）。
- 资源释放：shutdown 命令到进程树全部消失、无孤儿。

### 3.3 重复与统计

- 每场景 N=7 次，**轮转交错执行**（A,B,C,D,A,B,C,D…），而不是按候选分批连续跑，以解耦机器热噪声与后台干扰。
- 报告中位数与 p95，附最小/最大值；先测一次环境噪声底（空转采样 10 分钟）。
- 测试机固定电源计划、断开无关后台更新；每次实验记录已安装的 WebView2 / Chromium 版本。

### 3.4 基线测量

对现有 ZCode（只读、不改配置）执行与 E1/E2 相同场景定义的采样，建立生产基线：空闲、普通 coding 任务、Browser Use 活跃、多会话四类（对应讨论报告 9.1）。基线数字供 E5 对照，不参与 Q1–Q3 的横向淘汰。

**E0 交付物：** 采样/汇总脚本、场景定义文件、ZCode 基线报告。预算约 2–3 人日。

## 四、E1：内核语言对比实验（回答 Q1）

**范围：** headless、无 UI、无浏览器。用 Rust、Go、TypeScript(Node)、C#(.NET) 各实现一个满足附录 A 契约的**最小内核**，功能清单固定为：

1. 消费 mock provider 的 SSE 流并转发 delta 事件；
2. 工具调度：文件读取、子进程执行（带超时、取消、进程树清理）；
3. 工具元数据（只读/破坏性、超时、输出预算）与权限裁决回调桩；
4. 上下文截断（按 token 预算裁剪最旧工具结果）；
5. SQLite 会话持久化（WAL 模式，每 turn 落盘）；
6. JSONL 事件输出口与 SIGTERM/CTRL 干净退出；
7. 多会话并发（1/4/16 会话三档）。

明确不实现：压缩摘要、子代理、MCP、Provider 真实网络栈。这些留给 E4/E5，防止 E1 变成四个小产品。

**工作负载：** 附录 C 的"标准剖面"：200 turns，每 turn 约 500 个 SSE 事件、约 1 次工具调用（fs/exec 各半），exec 中 10% 在 100ms 处注入取消，第 100 turn 触发一次截断。mock provider 为本地 HTTP 服务，按回放脚本以固定 10ms/事件节奏输出，四个语言被测件连接同一实例。

**指标：**

| 指标 | 场景 | 说明 |
| --- | --- | --- |
| idle / settle / peak Private Bytes | 1、4、16 会话 | 主指标；settle 报告强制回收前后两值 |
| 流式首字节转发开销 | 标准剖面 | p95 |
| 事件回调延迟 | 标准剖面 | `model_delta` 时间戳相对 mock 发出时间的 p99 |
| 工具调度开销 | 标准剖面 | 命令进入→子进程启动→完成回收 |
| 取消响应 p99 | 取消注入点 | 到进程树退出 |
| 冷启动到 ready | 单次 | 7 次取中位 |
| 分发体积 | — | 二进制/运行时自包含包大小 |
| CPU 时间 | 标准剖面 | 进程树累计 |

**判定（建议默认门限，待确认）：** idle（1 会话）私有内存 >250 MB 记致命标记，>150 MB 记警告；16 会话线性外推偏差 >2× 记警告；取消响应 p99 >2 s 记致命。未触发门限者按实测值相对排序进入评分矩阵。

**预算：** 共享契约与回放服务器 2 人日 + 每语言 3–4 人日 ≈ 14–18 人日。

## 五、E2：浏览器执行形态对比实验（回答 Q2）

**前提：** 浏览器执行层与内核语言解耦（讨论报告 6.3），统一用 TypeScript/Playwright 适配层实现，内核侧只定义与 `BrowserControlPort` 等价的边界接口。本实验比较的是**执行形态**，也是候选 A/B 分叉前提（内嵌 vs 独立）的数据来源。

### 5.1 被测模式

| 模式 | 说明 | 对应现状 |
| --- | --- | --- |
| M1a | Playwright 启动捆绑 Chromium，headless，每任务起停 | 现独立后端行为（讨论报告 4.2），作基线复测 |
| M1b | Playwright headed + 持久 user-data-dir（专用 profile） | 候选 A 的完整形态：登录持久、可人工接管 |
| M2 | Electron `<webview>` + `webContents.debugger` CDP 控制 | 现桌面路径行为（讨论报告 4.1），最小原型复现 |
| M3 | CDP 直连用户真实 Chrome（`--remote-debugging-port`） | 候选能力：复用现有登录态，不新装浏览器 |

### 5.2 能力矩阵（清单见附录 B）

对附录 B 的 15 项能力逐项打分：`原生支持 / 组合实现 / 不可行`。定位与输入、截图、多标签、弹窗、登录持久化、崩溃后无孤儿退出为**关键项**——任一形态关键项出现 2 项以上"不可行且无缓解方案"，该形态不得作为主路径。

### 5.3 资源与时序指标

- 冷启动到首次导航完成、热复用到首次导航完成（M1a/M1b/M2）。
- 1 页、5 页活跃时的浏览器进程树 Private Bytes（按 3.1 口径）。
- 全部页面关闭并触发回收后的 `browser-closed` 内存；"浏览器不用时能否退出"（讨论报告 4.3）。
- 50 次开页/关页循环后的 `soak-delta`（泄漏检查）。
- 强杀宿主进程后：Chromium 子进程是否残留（孤儿检查）；重启后 profile 会话是否可恢复。
- M3 单列：接管已打开标签页、与用户手动操作并发时的稳定性。

**产出：** 能力矩阵 + 资源时序表。注意该表回答"哪种形态可行、代价多少"；**内嵌体验是否为硬性产品要求仍由用户决策**，本实验只提供代价数据。

**预算：** 6–8 人日。

## 六、E3：桌面外壳对比实验（回答 Q3）

**范围：** 只比外壳宿主成本，不含内核。用 Tauri 2、Electron、Wails、Avalonia 实现同一个参照 UI：消息列表渲染 1000 条历史消息 + 一路 20 事件/秒的流式文本追加 + 一个触发取消的按钮。

**指标：**

- 外壳进程树 idle 与"1000 条已渲染"两个检查点的 Private Bytes / Working Set。
- 安装包/自包含目录体积。
- 冷启动到主窗口可交互。
- Windows 依赖说明：Tauri/Wails 依赖系统 WebView2 运行时（锁定版本并记录），Electron 自带 Chromium，Avalonia 无 WebView。系统 WebView2 与 Electron Chromium 的渲染差异记为定性观察项。

**明确告诫（引用讨论报告 6.1）：** 外壳轻不等于全系统内存最低——Browser Use 活跃时，Tauri 方案会同时存在 UI WebView 与自动化 Chromium。全系统内存结论以 E5 的组合测量为准，E3 只决定 UI 宿主本身的代价。

**预算：** 3–4 人日。

## 七、E4：开发成本实验（回答 Q4）

**范围：** 在 E1 产出的四个内核 spike 上，各完成同一组标准变更任务（对应讨论报告第八节"应继承的行为"），任务书给出输入输出规格与验收用例，不给实现提示：

| 编号 | 变更任务 | 考察点 |
| --- | --- | --- |
| D1 | 工具执行中途取消：终止子进程树（Windows Job Object），清理子孙进程并上报 | 取消传播、进程治理 |
| D2 | 上下文压缩：触发条件、微压缩 + 摘要压缩两级，摘要后保持工具调用配对完整 | 上下文治理 |
| D3 | 崩溃恢复：kill -9 后重启，会话从 SQLite 恢复，命令去重与陈旧消息防护 | 持久化语义 |
| D4 | 新增第二个 mock provider：工具调用 ID、stop reason、缓存控制、流式结束语义保持不丢 | Provider 边界（原则 5） |
| D5 | 权限裁决：按只读/破坏性/并发安全元数据路由审批回调，审批超时默认拒绝 | 工具权限 |

**度量：**

- 黑盒验收：共享的语言中立测试套件（走附录 A 契约）通过率与发现的缺陷数——**主指标**。
- 改动面：LOC 增量、触达文件数、新增依赖数。
- 反馈周期：clean build 时间、增量 build + 全量测试时间。
- 实现耗时：由执行者自报，仅记录，**不计入评分**（见 12.1 混淆因素）。

**产出：** 四语言 × 五任务的成本表；同时对"稳定公开 API / 依赖内部实现"的比例做一次盘点（讨论报告 9.3：SSE、WS、SQLite、PTY、文件监听、进程树、diff、tree-sitter 各语言的可用库形态）。

**预算：** 4–5 人日。

## 八、E5：端到端整合原型（回答 Q5，仅幸存者）

**进入条件：** 通过 E1–E4 门禁的候选组合（预期为候选 A、B 中的一个或两个，也可能是重组组合，如 Go 内核 + 独立浏览器）。

**最小范围：** 内核（E1 spike 扩展 D1–D5）+ 浏览器执行层（E2 胜出形态）+ 最简 UI（E3 任意外壳）+ 真实 provider。

**三组测试：**

1. **生产任务回放。** 从用户现有 ZCode 使用记录中整理 10 个任务（5 纯 coding、3 浏览器、2 混合），固定模型、提示词与工具契约，在原型与 ZCode 基线上跑同任务，比较完成率、耗时、token 消耗、进程树内存峰值（对应讨论报告 9.4）。
2. **2 小时 soak。** 4 会话并发，周期性浏览器开页/关页/关闭回收，记录内存轨迹斜率、残留页面、页面数上限行为。
3. **中断注入矩阵。** 工具执行中取消、流式中途断网、turn 中 kill 内核、浏览器进程崩溃，各 ≥5 次，验证恢复语义与孤儿清理。

**判定（建议默认门限，待确认）：** soak 2 小时私有内存增长 >20% 记警告；任何中断场景留下孤儿 Chromium/子进程记致命；生产任务完成率低于 ZCode 基线 20 个百分点记警告。

**预算：** 每原型 8–12 人日。

## 九、判定框架

### 9.1 门禁汇总

| 门 | 实验 | 致命条件（建议默认） |
| --- | --- | --- |
| G1 | E1 | 内核 idle 私有内存 >250 MB；取消 p99 >2 s |
| G2 | E2 | 关键能力 ≥2 项不可行且无缓解 |
| G3 | E3 | 外壳 idle 进程树 >400 MB（仅警告，不淘汰） |
| G4 | E4 | 黑盒验收存在规格性失败项且无修复路径 |
| G5 | E5 | 中断场景孤儿进程；soak 增长失控 |

### 9.2 评分矩阵

对幸存候选按四维加权（0–5 分），权重**待用户输入**，建议默认：性能 20%、内存 25%、开发维护 30%、浏览器能力 25%。数据来源：性能/内存 ← E1+E3+E5；开发维护 ← E4；浏览器能力 ← E2+E5。

### 9.3 问题到决策的映射

- 内核语言 ← Q1 + Q4；
- 浏览器形态 ← Q2 数据 + 用户对内嵌体验的产品决策；
- 桌面外壳 ← Q3 + 全系统内存（E5）；
- 最终组合 ← Q5 对照 ZCode 基线。

## 十、执行顺序与预算

```text
E0 (2–3d)
 └─┬─ E1 内核 ×4 (14–18d)   ← 并行
   ├─ E2 浏览器形态 (6–8d)   ← 并行
   └─ E3 外壳 ×4 (3–4d)     ← 并行
       └─ E4 开发成本 (4–5d，依赖 E1 产物)
           └─ E5 端到端 ×1–2 原型 (8–12d/个)
```

- **完整路径：** 约 40–50 人日。
- **精简路径（约 25–30 人日）：** E0 + E1 + E2 + E3 + E4 精简版（只做 D1、D3、D4），E5 只做最终领先组合 1 个原型。适合先用数据收敛到 2 个以内组合，再决定是否完整验证。

## 十一、开始执行前需要用户确认的输入

以下槽位不填，实验只能产出相对数据，无法触发门禁淘汰：

1. 四维权重（9.2，建议默认 20/25/30/25）。
2. G1/G3/G5 的具体门限数值是否采纳建议默认。
3. 内嵌浏览器是否为硬性产品要求（决定候选 B 是否直接保留，还是等 E2 数据后再定）。
4. E5 生产任务回放集的 10 个任务选取（需要用户提供 ZCode 历史中的成功/失败案例）。
5. OS 沙箱评估是否纳入本轮（默认不纳入，另行立项；讨论报告 3.3）。
6. 平台范围（默认本轮仅 Windows，macOS/Linux 复测另行安排）。

## 十二、风险与局限

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 12.1 开发者语言熟练度污染 E4 | 实现耗时不公平 | 耗时不计入评分；以黑盒规格验收为主指标；任务书不给实现提示 |
| 12.2 单机 Windows | 结论不完全外推到 macOS/Linux | 记录为局限；关键指标（内核内存）跨平台差异相对小，外壳差异大 |
| 12.3 mock provider 与真实流差异 | E1 时序偏乐观 | E5 用真实 provider 复核；mock 节奏按实测真实流的 chunk 间隔校准 |

## 附录 D：实施状态（2026-10-19 更新）

用户已授权并要求先行实施 E1（内核测量）与 E0 的必要子集；Browser Use 明确为 built-in plugin，通过内核的工具调用边界接入，不与内核耦合，E2 维持独立。2026-10-19 追加两项补充变体实验（用户指定）：[1] Rust→WASM（同一 Rust 源码编译 wasm32-wasip1，wasmtime 运行）；[2] 同一份 JS 内核源码在 Bun 与 Node 上对比。

- 实现位置：`experiments/e1-kernel/`（契约、七个被测变体、mock provider、驱动器、采样器、运行器，见其 README）。
- 七变体：TCP 传输四内核 node/go/rust/dotnet；补充三变体 bun（与 node 同源 JS，bun:sqlite）、rustfeed（stdin 事件喂入传输的 Rust 内核，原生二进制）、wasm（rustfeed 同源编译的 wasm32-wasip1 模块，wasmtime v49 运行）。全部通过黑盒契约一致性测试（`node harness/conform.mjs all`）。
- 已完成：medium 剖面 1/4/16 会话 × 7 变体正式测量（`results/official-medium-7v/`，21 运行全部干净退出），结论存档于 `Docs/e1-kernel-first-results-2026-10-19.md`。四内核首测要点：稳态内存 Rust 显著领先、Node 驻留最高且 gc 不回落、16 会话峰值四者趋同、Go 峰值跨重复波动大。补充变体要点：**WASM 相对原生 Rust 固定开销约 +3.8MB/×1.6 且随会话数持平**（流式工作负载下 wasm 线性内存不增长），ready +11ms；**Bun 同源对比 Node 稳态高一个量级（idle 252–266MB vs 26–38MB）**，但时延与正确性与 Node 完全同级；WASI p1 无 socket/无进程派生/无线程/无 C 工具链四项约束均被实测证实，意味着 WASM 形态的内核必须依赖宿主扩展补齐网络与 exec。单重复数据不足以触发第九节门禁。
- 仍未执行：E2–E5；standard 剖面 N≥3 完整统计（`--profile standard --reps 7`）留待安排；.NET Native AOT 为可选加测项。
